# Расширение заказов в админке

**Приоритет:** P1

## Контекст

Блок ТЗ: заказ должен полноценно отображаться в админке, включая клиента, товары, фото, оплату, доставку и переходы к товару.

## Что найдено в проекте

- Resource заказа магазина: `app/Filament/Resources/ShopOrders/ShopOrderResource.php`.
- Страница редактирования: `app/Filament/Resources/ShopOrders/Pages/EditShopOrder.php`.
- Позиции заказа: `app/Filament/Resources/ShopOrders/RelationManagers/ItemsRelationManager.php`.
- Сейчас админка показывает только `id`, `user.email`, `status`, `total`, `notes`, `items_count`, `created_at`.
- В заказе отсутствуют поля гостевого клиента, доставки и оплаты.

## Что нужно сделать

1. Расширить карточку заказа под новую фактическую структуру заказа магазина.
2. Вывести блоки:
  - данные покупателя;
  - состав заказа;
  - оплата;
  - доставка;
  - комментарий;
  - служебные ссылки.
3. Добавить удобные переходы:
  - в карточку товара в Filament;
  - в карточку товара на storefront, если URL известен и хранится/строится предсказуемо.
4. Продумать read-only и editable поля по ролям менеджера.

## Backend

- При необходимости добавить eager-loading и resource accessors для удобного отображения в админке.
- Если storefront URL формируется на backend, нужен единый helper/конфиг базового URL.

## Admin

- Переработать `ShopOrderResource` form/table.
- Переработать `ItemsRelationManager`, чтобы выводить:
  - название товара;
  - артикул, если появится;
  - изображение;
  - количество;
  - цену;
  - ссылки на товар.
- Добавить отдельные поля для оплаты и доставки.
- Возможно добавить фильтры по оплате и способу доставки.

## Frontend

- Frontend вне репозитория.
- Если нужна ссылка на товар на сайте, нужно согласовать стабильный публичный URL товара.

## Database

- Использует поля, добавляемые задачами по guest checkout, доставке, оплате и артикулу/остаткам.

## API

- Для этой задачи внешние API не являются основной зоной изменений, кроме тех случаев, когда админка опирается на новые поля модели.

## Swagger/OpenAPI

- Изменения косвенные: документация должна отражать поля заказа, которые затем отображаются в админке.

## Notifications

- Поля админки должны совпадать с данными, уходящими в email/Telegram, чтобы менеджер видел единый источник истины.

## Tests

- Feature/интеграционные тесты на сохранение расширенных полей заказа.
- При наличии admin-тестов проверить отображение критичных колонок/секций.

## Acceptance criteria

- Менеджер видит полный состав заказа, клиента, оплату и доставку.
- Из заказа можно быстро перейти к товару.
- Информация по заказу читаема и пригодна для ручной обработки доставки.

## Важные ограничения

- Не ломать текущую Filament-структуру разделения Astro-x и Мёд.
- Не подтягивать доставку из внешних API, использовать только сохранённые данные заказа.

## Notes

- Изменяемым оставлен только `status` заказа. Остальные поля отображаются как read-only, поскольку в проекте нет отдельной ролевой модели менеджеров и не нужно открывать произвольное редактирование заказа.
- Ссылка на storefront строится только из сохранённых данных заказа/товара и не требует frontend-кода в этом репозитории.
- Автотесты и `pint` в текущем окружении не запускаются из-за отсутствующего PHP extension `mbstring`.
